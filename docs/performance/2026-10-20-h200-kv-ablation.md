# H200 KV 캐시·청크 분할 비교

기본 설정은 **BF16 가중치 + SDPA + 원본 KV 캐시 + 1청크**를 유지한다.
현재 Transformers/HQQ 방식의 KV 양자화는 이 H200 실험에서 느렸다.
2청크는 전체 녹음에서 약 19% 빨랐지만 출력 변화가 커서 자동 기본값으로 채택하지 않았다.

## 측정 조건

- 장치: juyu-h200의 NVIDIA H200 GPU 0~3, 각 143771 MiB, 드라이버 580.126.16.
- 입력: 같은 65분 37.131초 녹음과 앞 30분. 원본은 수정하지 않았다.
- 모델: OpenMOSS-Team/MOSS-Transcribe-Diarize, snapshot `704aa4a9c304e8520be88901e0d1960158ef5b15`.
- PyTorch 2.8.0+cu128, Transformers 5.20.2, HQQ 0.2.8.post1.
- 가중치는 모두 BF16로 고정. 모델 가중치의 8bit/4bit 양자화 실험이 아니다.
- KV: 원본 DynamicCache 또는 HQQ 8bit/4bit, group=64, residual=128, key/value axis=1.
  워밍업에서 실제 `QuantizedCache` / `HQQQuantizedLayer` 사용을 확인했다.
- greedy decoding, seed=0, 청크마다 최대 32768 출력 토큰. 완료한 경우 토큰 상한에 도달하지 않았다.
- GPU 하나에서 청크를 순서대로 처리. 2청크에는 경계 전후 총 30초 브리지 전사 시간도 포함했다.
- 모델 로딩·10초 워밍업·전송·오디오 분할·마지막 화자 병합은 추론 시간에서 제외했다.
  입력 특징 준비와 텍스트 디코딩은 포함했다. 앱 전체 소요 시간과 직접 비교하면 안 된다.

## 시간과 메모리

| 입력 | KV 캐시 | 청크 | 추론 시간 | Peak allocated | Peak reserved |
|---|---|---:|---:|---:|---:|
| 앞 30분 | 원본 | 1 | **3분 08초** | 5.91 GiB | 7.21 GiB |
| 앞 30분 | 원본 | 2 + 브리지 | 3분 06초 | 3.78 GiB | 4.27 GiB |
| 앞 30분 | HQQ 8bit | 1 | **7분 19초** | 5.21 GiB | 6.12 GiB |
| 앞 30분 | HQQ 4bit | 1 | **15분 초과, 중단** | 측정 미완료 | 측정 미완료 |
| 전체 65분 37초 | 원본 | 1 | **8분 49초** | 10.85 GiB | 14.49 GiB |
| 전체 65분 37초 | 원본 | 2 + 브리지 | **7분 08초** | 6.39 GiB | 8.07 GiB |

메모리는 `torch.cuda.max_memory_allocated/reserved` 값이다. 드라이버·CUDA context 등을
포함한 전체 GPU 사용량과는 다르며, 일반화된 VRAM 상한으로 사용할 수 없다.

8bit KV는 원본보다 2.34배 오래 걸렸고 최대 할당 메모리는 약 11.8% 줄었다.
30분 디코딩 처리량도 원본 76.4 tokens/s, HQQ 8bit 32.8 tokens/s로 차이가 났다.
4bit는 900.66초 시점에 끝나지 않아 중단했다. 마지막 진행 기록은 23041 토큰이다.
이 경우 완료 시간·정확도·최대 할당 메모리를 지어내지 않았다.

전체 녹음은 30분 측정값을 길이 비율만큼 곱한 약 6분 50초보다 약 29% 오래 걸렸다.
한 녹음에서 관찰한 값이므로 모든 녹음의 시간 증가율이라고 단정할 수 없다.

## HQQ가 느려진 이유

이번 결과는 현재 Transformers/HQQ 경로의 메모리 절약 비용으로 해석한다.
[Transformers 5.20.2의 `QuantizedLayer.update`](https://github.com/huggingface/transformers/blob/v5.20.2/src/transformers/cache_utils.py#L650-L686)는
디코딩 때 저장된 K/V를 역양자화하고 원본 정밀도 캐시와 이어 붙이며, residual 구간이
차면 누적 캐시를 다시 양자화한다. 이번 residual 설정은 128토큰이다. 원본 KV의
SDPA 경로에 이런 변환·메모리 이동이 추가된다. 낮은 정밀도의 KV로 attention을 직접
계산하는 fused 커널과는 실행 경로가 다르다.

H200에서는 원본 KV도 VRAM에 충분히 들어가므로 양자화가 OOM이나 CPU offload를
피해 주는 이득이 없었다. 추가 변환 비용이 유력한 원인이지만 커널별 프로파일링으로
비용을 분리하지 않았으므로, 모든 지연을 특정 연산 하나의 탓으로 확정하지 않는다.
메모리가 부족한 GPU나 다른 엔진에서는 결론이 달라질 수 있다.
예를 들어 [vLLM의 FA3 FP8 KV 경로](https://docs.vllm.ai/en/v0.17.0/features/quantization/quantized_kvcache/)는
양자화된 영역에서 attention을 수행할 수 있지만, 이번에 MOSS 호환성이나 성능을 검증한 것은 아니다.

## 출력 비교

각 길이의 원본 KV·1청크 결과를 비교 기준으로 삼았다. **사람이 만든 정답이 없으므로
아래 본문 차이는 실제 인식 오류율이 아니고, 화자 일치율은 DER이 아니다.**
본문 비교는 공백·문장부호를 제외한 문자 편집 거리이며, 화자는 라벨 순열을 맞춘 뒤
겹치는 구간에서 비교했다. 2청크는 앱의 실제 30초 브리지 화자 병합 코드를 적용했다.

| 입력·설정 | 기준 대비 본문 차이 | 겹친 구간 화자 일치 | 출력 화자 ID 수 | 마지막 타임스탬프 |
|---|---:|---:|---:|---:|
| 30분 원본·1청크 | 기준 | 기준 | 3 | 1799.18초 |
| 30분 원본·2청크 | 2.69% | 89.65% | 5 | 1799.14초 |
| 30분 KV 8bit·1청크 | 0.66% | 99.89% | 3 | 1799.18초 |
| 전체 원본·1청크 | 기준 | 기준 | 2 | 3937.10초 |
| 전체 원본·2청크 | 6.14% | 68.77% | 6 | 3873.41초 |

전체 2청크 결과는 마지막 타임스탬프가 기준보다 63.70초 일찍 끝났다. 이것만으로 누락을
확정할 수는 없지만, 속도 이득만 보고 기본값으로 바꾸기에는 위험 신호다. 원본·1청크
결과 역시 정답으로 검증된 것은 아니다. 화자 ID 수가 실제 사람 수를 뜻하지도 않는다.

## 반복·CPU 스레드 확인

30분 원본·1청크는 GPU 0에서 187.64초, GPU 3에서 반복했을 때 199.11초였다.
GPU 1에서 서버 기본값인 CPU 64스레드로 실행한 경우 192.51초였다. 세 결과의 본문과
화자 출력은 같았다. GPU·실행 시점도 달라 스레드 효과만 분리한 실험은 아니며,
반복 변동 약 6.1% 안에서 뚜렷한 스레드 수 개선을 주장할 수 없어 기본값을 바꾸지 않았다.

전체 길이 실험과 반복 실행에는 5초 간격 GPU 관측이 있다. 원래 실행 중이던 GPU 더미
프로그램은 실험을 감지하고 자동으로 물러났다. 관리 프로세스는 중지하지 않았다.
관측 구간에서 실험 외의 비더미 GPU 프로세스는 없었다. 첫 30분 기준 실행은 연속 관측이
끝까지 있던 것이 아니며, 중간 수동 프로세스 확인과 이후 반복 실행으로 보완했다.

## 앱 반영

2026-10-21 반영 기준:

- 이 측정은 `src/performance_seeds.json`의 초기 자료로 저장했다. 추정 코드는 GPU 이름별 고정 분기 대신 공통 성능 프로필을 사용한다. 다른 CUDA GPU도 완료된 전사의 청크·브리지 시간과 예약 메모리를 설정별로 누적해 보정한다. 모델·정밀도·실행 설정·소프트웨어 버전이 다른 자료와 실패·출력 한도 도달 결과는 섞지 않는다.

- 서버의 가중치·KV 양자화 선택과 관련 의존성 설치를 제거했다. 서버는 원본 BF16/FP16을
  사용하며 Mac의 MLX 양자화는 유지한다. 기존 서버 양자화 설정은 원본으로 전환하고
  청크·토큰·모델 경로는 보존한다. 기존 서버 환경이나 캐시는 삭제하지 않는다.
- 예상 시간은 범위 대신 한 값으로 표시한다. 원본 BF16/SDPA의 네 결과를 모두 사용한다.
  총 길이 D, 청크 수 N, 화자 연결 길이 B에 대해
  `T = N × f(D/N) + (N−1) × 2.674초 × B/30초`로 계산한다.
  2.674초는 두 브리지 실측의 평균이다. 2청크 총시간에서 이 값을 빼고 2로 나눠
  청크당 비용을 구한 뒤 15분·30분·32분 49초·65분 37초 네 기준점 사이를 구간별로
  선형 보간한다. 따라서 전체 길이에 단일 배율을 곱하는 방식과 달리 긴 청크의
  처리 비용 증가와 순차 실행·브리지 비용을 반영한다.
- H200 Peak Memory도 네 실측의 `peak reserved`를 청크 길이로 보간한 뒤 1 GiB를 더해
  표시한다. 할당된 텐서만 계산하면 드라이버·CUDA context·예약 메모리를 놓친다.
  전체 1청크의 프로세스 VRAM 관측 최대는 15.17 GiB, 2청크는 8.75 GiB였으므로
  이 여유를 포함했다. 순차 청크의 메모리는 합산하지 않는다.

| 입력 | 원본 KV 설정 | 예상 시간 | 예상 Peak Memory |
|---|---|---:|---:|
| 30분 | 1청크 | 약 03:08 | 약 8.2 GiB |
| 30분 | 2청크 + 30초 브리지 | 약 03:06 | 약 5.3 GiB |
| 65분 37초 | 1청크 | 약 08:49 | 약 15.5 GiB |
| 65분 37초 | 2청크 + 30초 브리지 | 약 07:08 | 약 9.1 GiB |

이 표는 보정에 사용한 네 점을 재현한 결과이며 새 녹음에 대한 예측 정확도 검증이 아니다.
전체 H200·원본 BF16/auto·SDPA·KV 사용·32768 토큰·청크 90분 이하에서 적용한다.
15분보다 짧은 청크는 가장 짧은 실측점의 시간을 길이에 비례시켜 외삽한다. 메모리는
첫 구간의 기울기를 쓰되 실제 30초 브리지의 예약 메모리보다 작아지지 않게 한다.
65분 37초보다 긴 청크는 마지막 구간의 기울기로 외삽한다. 실측 출처와 외삽 여부는 API 메타데이터에 남기며 화면에는 예상값만 표시한다.
다른 장치·설정·길이는 초기 추정 한 값을 사용한다. 실행 여유 경고는 별도의 내부 상한
`reserved × 1.25 + 1 GiB`를 사용한다. 표시값과 내부 여유는 통계적 신뢰구간이 아니다.
시간은 모델 로딩·전송·마지막 병합을 제외한 추론 기준이며, 녹음의 발화 밀도·토큰 수나
서버 부하가 달라지면 오차가 생길 수 있다. 4bit 중단 결과는 완료 성능 데이터에 넣지 않았다.

## 재현 자료

정확한 초 단위 측정, 생성 토큰, 각 청크·브리지 시간과 설정은
[JSON 기록](2026-10-20-h200-kv-ablation.json)에 있다. 오디오와 전사 본문은 포함하지 않는다.

`scripts/benchmark-cuda.py`는 앱과 분리한 과거 실험 재현용이다. 준비된 CUDA 환경에서 `--gpu GPU-... --model <cached snapshot>
--audio <private WAV> --output <private directory> --kv-bits 0|8|4 --chunks 1|2 --seconds 1800`으로
실행한다. `--seconds 0`은 전체 길이다. `PYTHONPATH`에 이 프로젝트를 두고, HQQ는 준비된
별도 환경이나 실험용 의존성 overlay에서 사용한다. 공유 환경을 실험 때문에 변경하지 않는다.
청크별 기본 추론 제한은 900초(`--budget-seconds`)이며, 초과한 경우 미완료로 기록한다.

결과 비교는 `scripts/summarize-cuda-benchmark.py`와 `rapidfuzz==3.14.3`을 사용한다.
캐시 전략과 일반적인 지연 시간 제약은 [Transformers 공식 문서](https://huggingface.co/docs/transformers/kv_cache)를 참고한다.
이 결과는 현재 HQQ 방식에 해당하며, 다른 엔진의 fused FP8 캐시 성능을 뜻하지 않는다.
